## Règle d'utilisation

- **Règle de branche KillEngine (décision propriétaire, 29/08/2026)** : travailler et committer directement sur `main`. Ne pas créer de branche `agent/...` dans ce dépôt.
- Ajouter les nouvelles phases ici, en bas de fichier, avec quoi/pourquoi/comment vérifié.
- Ne pas remettre tout l'historique dans ce fichier : dès qu'une phase est close, transférer le détail complet vers `docs/PHASE_TRACKER_HISTORY.md` et ne garder ici qu'un renvoi court.
- Ne jamais supprimer d'historique sans transfert explicite.
- Pour les gros détails d'une phase future, préférer un document dédié dans `docs/` puis garder ici un résumé avec lien.
- **Build complet KillEngine = long, ne pas vérifier l'état en boucle.** Un build complet (`scripts/build.ps1`, voir [[killengine_build_wrong_ninja_in_path]]) prend plusieurs minutes. Claude le lance en arrière-plan (`run_in_background: true`) et reçoit une notification automatique dès qu'il se termine — inutile de le sonder entre-temps (pas de `Get-Process`/poll en boucle, pas de nouvelle commande "pour vérifier"). Ne jamais tuer un build en cours pour le relancer ou pour lancer autre chose en parallèle : ça ne fait que perdre le travail de compilation déjà fait et repartir de zéro. Attendre la notification de fin, puis seulement agir sur le résultat.
- **Seuls Codex et Claude sont habilités à lancer un build sur ce dépôt** (décision propriétaire, 04/09/2026). Les autres agents (Cline, Roo, etc.) écrivent/proposent le code mais consignent ici que le build/les tests restent à faire par Codex ou Claude, plutôt que d'exécuter `scripts\build.ps1` eux-mêmes.

#### UX-CHECKUP-2 — corriger les suggestions de type/facteur Auto

**Diagnostic / reproduction (Codex, 22/09/2026)** : sans lancer de scan, saisir `50` puis cliquer `Int32 x4096` laisse la valeur à 50 et vide le sélecteur (`selectedIndex:-1`) — le bouton n'a aucun effet utile. **Fichiers / cause (à revérifier)** : `ui/src/stores/app.ts:4440` génère cinq facteurs de suggestion, mais `useInferredType` (ligne 4451) ne traite réellement que le facteur x100 et écrase directement le champ de saisie avec le résultat. Boutons appelants : `ui/src/components/expert/ExactScanPanel.vue:54`.

**Correctif attendu / pièges** : séparer trois données distinctes — valeur affichée (saisie utilisateur), type natif choisi, facteur appliqué — et calculer chaque suggestion depuis la valeur affichée d'origine, jamais depuis un résultat déjà transformé (l'action doit être idempotente : cliquer deux fois le même facteur donne le même résultat). Étendre le traitement aux cinq facteurs générés, pas seulement x100. Aperçu explicite recommandé par le rapport (ex. « 50 affiché → 204800 stocké, Int32 ×4096 »). Tester aussi la perte de précision sur des valeurs proches des bornes du type natif.

**Validation exigée avant clôture** :
- [x] Chaque facteur généré (pas seulement x100) produit un résultat correct depuis la valeur affichée.
- [x] Clics répétés sur le même facteur : résultat stable (idempotent), pas de multiplication cumulative.
- [x] Valeur proche d'une borne du type natif : comportement explicite (troncature signalée ou refus), pas un débordement silencieux.
- [x] Sélecteur de type reste cohérent avec le résultat affiché après un clic.

**Cause confirmée (22/09/2026, Claude)** : diagnostic Codex exact sur le symptôme, incomplet sur la cause. `useInferredType()` (`ui/src/stores/app.ts`) ne gérait bien qu'un seul facteur en dur (`typeLabel.endsWith('x100')`), laissant les 4 autres (x10/x1000/x4096/x65536) écrire le libellé entier (ex. `"Int32 x4096"`) comme type de scan — un type invalide, absent des `<option>` du sélecteur, d'où `selectedIndex:-1`. Cause plus profonde du « multiplie à chaque clic » : `inferredExactTypes` est un `computed` réactif à `exactScanValue` lui-même — dès qu'un clic de suggestion réécrit `exactScanValue` (50→5000), la LISTE de suggestions se recalcule aussitôt depuis cette nouvelle valeur (le bouton visuellement « x100 » représente alors 5000×100, pas 50×100 à nouveau) ; ce n'était pas une accumulation dans `useInferredType` mais un recalcul de la base elle-même à chaque render. Bonus trouvé en creusant le template : `ExactScanPanel.vue` surlignait le chip actif avec `.replace(/\\s+x100$/i, '')` — double antislash dans une expression JS de template (donc `\\s` = antislash littéral + s, jamais un espace) : ce surlignage n'a probablement **jamais** fonctionné, même pour x100, depuis son écriture.

**Correctif (22/09/2026, Claude, frontend uniquement)** :
1. `ui/src/stores/app.ts` : nouvelle `exactScanValueBaseline` (ref séparée de `exactScanValue`), synchronisée par un `watch(exactScanValue, ..., {flush:'sync'})` sauf quand l'écriture vient de `useInferredType` lui-même (drapeau `suppressBaselineCapture`, nécessite `flush:'sync'` pour être actif au bon moment — un `watch` par défaut est asynchrone). `inferredExactTypes` calcule désormais depuis cette base stable, pas depuis `exactScanValue` courant : la liste de suggestions ne bouge plus sous les pieds de l'utilisateur après un clic.
2. `useInferredType()` réécrite : extraction générique du facteur via `/^(.*?)\s+x(\d+)$/i` (au lieu du seul x100 en dur), calcul depuis `exactScanValueBaseline` (jamais depuis la valeur déjà transformée), refus explicite avec message FR/EN (`appStore.typeInference.scaleRefused`) si le résultat n'est pas fini ou dépasse les bornes Int32 (filet de sécurité — la génération des chips exclut déjà ces cas, donc ce chemin ne devrait normalement jamais être atteint par un clic réel). Un type non préfixé (ex. `Float32`) réinitialise désormais la valeur à la base d'origine plutôt que de laisser une valeur mise à l'échelle par un clic précédent.
3. `ExactScanPanel.vue` : regex de surlignage corrigée en simple antislash (`/\s+x\d+$/i`) — répare aussi le surlignage x100, cassé depuis l'origine.
4. Nouvelles clés FR/EN `appStore.typeInference.scaleRefused`.

**Tests réellement exécutés** : `npm run type-check` propre, `npm run build` OK. **Vérifié en direct sur l'application réelle** (`KillEngine.exe`/`KillEngineTestTarget.exe`, pipe + CDP, vue Expert réelle, vrais clics/saisies) :

   - Clic `Int32 x4096` → valeur `204800`, type sélectionné `Int32` (`selectedIndex:5`, plus `-1`) — reproduction exacte du cas du rapport, confirmée résolue.
   - Clic `Int32 x100` **trois fois de suite** depuis `50` (reproduction exacte du second cas du rapport) → `5000` à chaque fois, jamais `500000` — idempotence confirmée.
