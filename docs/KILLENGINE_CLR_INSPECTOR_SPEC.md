## Pourquoi ce chantier

Suite à `docs/KILLENGINE_CLR_TEST_TARGET_SPEC.md` (cible de test CLR dédiée), l'utilisateur a explicitement demandé d'aller jusqu'à un MVP fonctionnel plutôt que de laisser le candidat #8 (`docs/POWER_UP_ROADMAP.md`) en simple environnement de validation sans fonctionnalité réelle :

> "Puisque nous avons maintenant une cible .NET déterministe et automatisable, je préfère profiter de cette base pour aller jusqu'à un MVP ClrMD fonctionnel plutôt que laisser le chantier en attente."

Le MVP initial devait démontrer la chaîne complète **KillEngine → helper ClrMD → processus .NET cible → heap/types/champs/roots → résultat exploitable → test après GC**, avec une API/pipe propre. Depuis le 21/08/2026, KillEngine expose aussi cette capacité dans l'UI et déroule les collections courantes à profondeur bornée.

## Architecture

```
KillEngine.exe (C++/Qt, natif)
      │  ApplicationController + QLocalSocket JSON-RPC (UI CLR)
      ▼
KillEngineClrInspector.exe (helper .NET, tools/clr_inspector/)
      │  Microsoft.Diagnostics.Runtime (ClrMD) — DataTarget.AttachToProcess
      ▼
process .NET cible (n'importe quel PID avec un CLR chargé,
                     ex: KillEngineClrTestTarget.exe)
```

**Pourquoi un helper séparé et pas du code C++ direct** : ClrMD est une bibliothèque managée (.NET) — `KillEngine.exe` est natif C++/Qt et ne peut pas l'héberger directement sans un pont (hosting CLR in-process via `hostfxr`/`nethost`, ou sous-processus). Le MVP retient le **sous-processus + pipe JSON-RPC**, pas le hosting in-process : évite le risque de stabilité d'un CLR hébergé à côté de la boucle d'événements Qt (le projet a déjà un historique de crashes liés à des mécanismes bas niveau — breakpoints, injection — donc cette prudence est délibérée, pas une esquive), et permet de publier `KillEngineClrInspector` en **self-contained** (`dotnet publish -r win-x64`) pour ne pas exiger de runtime .NET installé chez l'utilisateur final.

**Décision de protocole** : le pipe (`KillEngineClrInspectorPipe`) utilise **exactement** le même format JSON-RPC ligne-par-ligne que `apps/desktop/automation_pipe_server.h` et `tests/clr_targets/KillEngineClrTestTarget`. Conséquence directe : `scripts/automation-pipe-call.ps1 -PipeName KillEngineClrInspectorPipe -Method ...` pilote ce helper sans aucune modification du script, et le jour où `ApplicationController` veut exposer cette capacité à l'UI, l'intégration consiste à lancer ce sous-processus et lui parler via le même mécanisme déjà maîtrisé, pas à inventer un nouveau protocole.

## Emplacement et build

- `tools/clr_inspector/KillEngineClrInspector/` — le helper lui-même (`net8.0`, dépendance NuGet `Microsoft.Diagnostics.Runtime` 4.0.732401).
- `tools/clr_inspector/KillEngineClrInspector.Tests/` — suite d'auto-tests bout-en-bout (xUnit).
- Nouveau dossier top-level `tools/` (distinct de `tests/clr_targets/`) : les cibles de test ne sont jamais livrées à l'utilisateur, ce helper est destiné à l'être à terme — séparation délibérée pour ne pas brouiller cette frontière.
- Pas construit par CMake (projet .NET). Build : `dotnet build tools/clr_inspector/KillEngineClrInspector -c Release`. Tests : `dotnet test tools/clr_inspector/KillEngineClrInspector.Tests -c Release` (construit automatiquement ses dépendances via les références de projet MSBuild, mais **pas** `KillEngineClrTestTarget` — celui-ci doit être construit séparément au préalable, voir `docs/KILLENGINE_CLR_TEST_TARGET_SPEC.md`).
- Packaging portable : `scripts/package-windows.ps1` publie maintenant le helper en self-contained Windows x64 sous `dist\KillEngine-portable\tools\clr_inspector\KillEngineClrInspector.exe` (`-SkipClrInspector` existe seulement pour les packages dev légers). `ApplicationController::findClrInspectorExecutable()` connaît déjà ce layout.

## Comment l'API ClrMD réelle a été déterminée

Plutôt que de deviner l'API depuis la mémoire d'entraînement (risque réel : la bibliothèque a beaucoup changé entre versions 1.x/2.x/3.x/4.x, et la version publiée sur NuGet au moment de ce chantier — `4.0.732401` — a un schéma de version inhabituel qui ne correspond à aucune version "connue" a priori), l'API a été vérifiée **par réflexion sur les métadonnées de l'assembly réellement restaurée** (`System.Reflection.Metadata.PEReader`/`MetadataReader`, script jetable dans le scratchpad de session) avant d'écrire une seule ligne de `ClrSession.cs`. Résultat : le code a compilé **sans aucune erreur au premier essai**. À refaire pour toute évolution future de ce module si la version de ClrMD est mise à jour et que le comportement change de façon inattendue.

## Surface pilotable (`ControlPipeServer` + `MethodDispatcher` + `ClrSession`)

| Méthode | Paramètres | Rôle |
| --- | --- | --- |
| `ping` | — | Smoke test |
| `attach` | `[pid]` | Détecte + attache un CLR sur le PID donné (`DataTarget.AttachToProcess(pid, suspend:false)` — attache **passive**, lit la mémoire live à la demande plutôt qu'un instantané figé, condition nécessaire pour pouvoir relire un état post-GC sans ré-attacher). Erreur claire si aucun CLR détecté (`dataTarget.ClrVersions.Length == 0`) |
| `detach` | — | Libère la session courante |
| `flushCachedData` | — | `ClrRuntime.FlushCachedData()` — à appeler après un GC déclenché en dehors de cette session, avant de rejouer un heap walk, pour invalider le cache interne de segments/heap de ClrMD |
| `findObjectsByType` | `[typeSubstring?]` (défaut `"KillEngine.ClrTestTarget"`) | `heap.EnumerateObjects()` filtré par sous-chaîne de nom de type, retourne adresse/type/taille |
| `findObjectsByFieldValue` | `[typeSubstring, fieldName, expectedValue, maxResults?]` | Locator borné `type + champ + valeur` pour retrouver un objet logique même si son adresse a bougé après un GC compactant. Supporte les champs string, primitifs simples et `null`, retourne les adresses candidates avec `identityField`/`identityValue` |
| `readObject` | `[addressHex]` | `heap.GetObject(address)` puis lecture générique de tous les champs déclarés du type : primitifs par valeur, `string` via `ReadStringField`, références d'objet par adresse+type, et déballage borné (`MaxCollectionItems=32`) des collections courantes (`List<T>`, tableaux 1D **et multidimensionnels**, `Dictionary<K,V>`, `HashSet<T>`, `Queue<T>`, `Stack<T>`, **`LinkedList<T>`, `SortedDictionary<K,V>`, `SortedSet<T>` depuis le 23/08/2026** — voir "Plus de collections BCL" ci-dessous). Ajoute `fieldDetails` avec type, adresse effective et drapeau `writable` pour les champs primitifs simples. Les champs struct-dans-struct sont déballés récursivement (borné à 4 niveaux, voir "Résolution récursive des structs imbriqués" ci-dessous). Gère nativement les cycles comme `Player.Self` sans boucle infinie |
| `writePrimitiveField` | `[objectAddressHex, fieldName, value]` | Écriture v1 bornée d'un champ primitif d'instance (`bool`, entiers 8/16/32/64 bits signés/non signés, `float`, `double`) : ClrMD résout l'adresse effective du champ (`ClrInstanceField.GetAddress`), le helper écrit les octets via `WriteProcessMemory`, puis relit le champ pour vérifier. Pas de `string`, référence objet, struct imbriquée ni tableau/collection dans cette v1 |
| `writePrimitivePath` | `[objectAddressHex, path, value]` | Écriture symbolique bornée dans le graphe managé : part d'une adresse objet actuelle, traverse des champs référence (`Self.Health`, `Inventory.Items[0].Value`, `Inventory.QuickSlots[1].Value`) et écrit le champ primitif feuille via la même primitive sûre que `writePrimitiveField`. Les index sont supportés sur tableaux et `List<T>` de références **et, depuis PHASE 59, sur tableaux/`List<T>` de PRIMITIFS** (ex: `Scores[2]`, `int[]`) — résolution d'adresse d'élément via `ClrType.GetArrayElementAddress`, dispatch automatique selon le type d'élément réel du champ collection. **Depuis PHASE 66**, un tableau/`List<T>` de STRUCTS est aussi traversable comme nœud intermédiaire (pas en feuille) : `Champ[i].SousChamp` compose `GetArrayElementAddress` (adresse de l'élément struct) puis `ClrInstanceField.GetAddress(interior: true)` (adresse du champ primitif à l'intérieur) — voir section dédiée. Écrire l'élément struct ENTIER par index reste hors scope (pas de valeur primitive unique à encoder). Les `Dictionary<K,V>` (valeurs internes déjà couvertes par ailleurs) restent hors scope pour l'indexation directe |
| `resolveInstanceMethodAddress` | `[objectAddressHex, methodName]` | **Livré le 22/08/2026, étendu PHASE 59 puis PHASE 65.** Résout l'adresse native déjà JITtée (`ClrMethod.NativeCode`) d'un setter d'INSTANCE réel pour permettre à KillEngine (côté natif) de l'appeler par injection shellcode plutôt que d'écrire son champ backing. Cherche le nom exact d'abord, puis retente avec le préfixe `set_` si absent (`"Health"` → `"set_Health"`). Valide : méthode trouvée, pas statique, 0 ou 1 paramètre explicite, et si 1, soit un type primitif supporté (`bool`, `int8/16/32/64`, `uint8/16/32/64`, `Single`/`Double` depuis PHASE 59), soit **depuis PHASE 65** un type RÉFÉRENCE (classe/string, résolu via `heap.GetTypeByName` + `IsValueType`) — jamais un type VALEUR/struct, rejeté explicitement. Retourne `{success, objectAddress, typeName, methodName, nativeCodeAddress, parameterType, parameterIsReferenceType, isStatic}`. Ne résout QUE l'adresse — ClrMD ne peut jamais exécuter de code lui-même (DAC passif) ; l'appel réel se fait côté natif, voir `ApplicationController::callClrInstanceMethod` plus bas |
| `enumerateRoots` | `[typeSubstring?]` | `heap.EnumerateRoots()` filtré par le type de l'objet racine, retourne l'adresse du root, son `RootKind` (`StrongHandle`/`Stack`/... — **jamais `StaticVar` sur ce runtime**, voir investigation ci-dessous), et l'objet pointé |
| `findStaticFields` | `[typeSubstring, fieldNameSubstring?]` | **Livré le 22/08/2026.** Résout des champs `static` directement via `ClrType.StaticFields`/`ClrStaticField`, indépendamment de `heap.EnumerateRoots()` — fonctionne en attache passive. Voir section "Limitation connue" pour le détail de l'investigation qui a mené à cette méthode |
| `findGcRootPath` | `[targetObjectAddressHex, maxDepth?, maxRootsScanned?]` | **Livré le 22/08/2026, converti en BFS multi-source garanti optimal le 23/08/2026.** Un seul BFS partant simultanément de TOUS les roots scannés (`heap.EnumerateRoots()`, bornés à `maxRootsScanned`, dédoublonnés) explore les champs de référence et éléments de tableau de chaque objet visité, jusqu'à `maxDepth` sauts, pour reconstruire le PLUS COURT chemin root→...→objet cible (`shortestPathGuaranteed: true`). Voir section dédiée plus bas pour le détail et les limites restantes |
| `generateObjectReport` | `[objectAddressHex, maxDepth?, maxNodes?, includeGcRootChain?]` | **Livré le 23/08/2026.** BFS borné (défaut profondeur 3 / 50 nœuds, max 6 / 300 — nettement plus faible que `findGcRootPath` car chaque nœud est décrit en entier, pas juste traversé) sur le graphe atteignable depuis un objet, réutilisant `EnumerateGcRootPathReferences` pour la traversée et `DescribeObject` (même sortie que `readObject`) pour chaque nœud. Retourne une liste PLATE de nœuds (pas un JSON arborescent) avec `discoveredVia` par nœud pour reconstruire la hiérarchie et gérer nativement les références partagées/cycles sans dupliquer leur contenu. Inclut optionnellement `gcRootChain` (réutilise `findGcRootPath` tel quel) pour montrer comment l'objet racine du rapport est lui-même atteint depuis un GC root. Voir section dédiée plus bas |
| `shutdown` | — | Arrêt propre |

**Nom de pipe paramétrable** (ajouté le 20/08/2026, pour les tests de régression ci-dessous) : variable d'environnement `KILLENGINE_CLR_INSPECTOR_PIPE_NAME`, sinon `ControlPipeServer.DefaultPipeName` (`KillEngineClrInspectorPipe`) — permet de lancer des instances isolées supplémentaires sans collision avec une instance déjà active. ## Appel de setter réel, livré le 22/08/2026

ClrMD est une API de lecture passive du tas managé (DAC) — elle n'a **aucun** mécanisme pour exécuter du code dans le process cible. Pour appeler un vrai setter de propriété C# (avec sa logique métier réelle — validation, événements, effets de bord — pas juste écrire le champ backing), le mécanisme retenu est :

1. Résoudre l'adresse native déjà JIT-compilée du setter via ClrMD (`ClrMethod.NativeCode`, méthode `resolveInstanceMethodAddress`).
2. Générer un petit shellcode x64 qui pose `this` en RCX, la valeur en RDX (si le setter attend un paramètre primitif entier) — ou en XMM1 (si le paramètre est `Single`/`Double`, PHASE 59, voir plus bas) — et `call` cette adresse native.
3. Injecter et exécuter ce shellcode via la primitive déjà existante et déjà testée `killcore::injectShellcode(process, shellcode)` (`core/inject/dll_injector.h/.cpp`) — pas de réinvention de `CreateRemoteThread`/`VirtualAllocEx`.
4. Revérifier l'état après coup en relisant l'objet via ClrMD (`readObject`), comme `writePrimitiveField` le fait déjà.

**Shellcode exact (x64, fixe)** :
```
sub rsp, 0x28                  ; 48 83 EC 28  (0x20 shadow space + 8 pour l'alignement 16 octets à l'entrée du call)
mov rcx, <objectAddress>       ; 48 B9 <8 octets little-endian>   (this)
mov rdx, <valueImmediate>      ; 48 BA <8 octets little-endian>   (SEULEMENT si le setter prend 1 paramètre)
movq xmm1, rdx                 ; 66 48 0F 6E CA  (SEULEMENT si le paramètre est Single/Double -- PHASE 59)
mov rax, <nativeCodeAddress>   ; 48 B8 <8 octets little-endian>
call rax                       ; FF D0
add rsp, 0x28                  ; 48 83 C4 28
xor eax, eax                   ; 33 C0
ret                             ; C3
```

**Setters à paramètre `float`/`double`, livré en PHASE 59** : la convention d'appel x64 Windows passe un 2ᵉ argument flottant en XMM1, pas RDX — le shellcode v1 (`mov rdx, imm64`) était donc incompatible avec ce cas et le rejetait explicitement. Résolu sans complexifier le parsing : `killcore::encodeInstanceMethodParameterImmediate` calcule déjà le bit pattern IEEE754 brut (via `killcore::parseScanValue`/`scanValueToBytes`, zero-étendu sur 64 bits pour un `float`, exactement 64 bits pour un `double`) — il suffisait de retirer le rejet explicite pour `Float32`/`Float64` et de charger ce bit pattern dans XMM1 au lieu de RDX. `buildCallInstanceMethodShellcode` accepte un paramètre `paramIsFloat` : quand vrai, le générateur ajoute `movq xmm1, rdx` juste après le `mov rdx, imm64` — RDX porte alors une valeur non pertinente pour l'appelée (registre caller-saved, aucun risque), seul XMM1 est lu par le JIT pour un paramètre flottant. `this` reste en RCX, inchangé. Côté helper .NET, `ClrSession.SupportedInstanceMethodParameterTypes` accepte désormais `Single`/`Double` en plus des entiers — `ClrSession` ne connaît toujours pas la convention d'appel, elle se contente de résoudre l'adresse ; c'est `ApplicationController` (natif) qui choisit RDX vs XMM1 selon le `parameterType` résolu. Preuve bout-en-bout : `Player.Vigor` (`double`, `ObjectGraph.cs`) reprend le patron de `Player.Vitality` (clamp `[0, VigorMax=100.0]` + compteur `_vigorChangeCount` séparé) — le test xUnit dédié écrit 250.0 par shellcode réel et vérifie que la valeur backing est bien clampée à 100.0 (pas 250.0), preuve que XMM1 a réellement été lu par le JIT et pas RDX.

**Scope — limites volontaires, documentées, pas contournées** :
- Setters d'INSTANCE uniquement (pas static — vérifié via `ClrMethod.Attributes & MethodAttributes.Static`), 0 ou 1 paramètre EXPLICITE.
- Si 1 paramètre : `bool`, `int8/16/32/64`, `uint8/16/32/64`, **`Single`/`Double` (PHASE 59, via XMM1, voir ci-dessus)**, ou **un type RÉFÉRENCE — classe/`string` (PHASE 65, voir section dédiée)** pointant vers un objet déjà existant sur le tas.
- Paramètre `struct` (type VALEUR) — **couvert pour le cas registre unique** (chantier "setters à paramètre struct", PHASE 76/79) : struct de taille totale exactement 1, 2, 4 ou 8 octets avec tous ses champs primitifs, passé PAR VALEUR packé octet à octet dans RDX (même shellcode que les entiers). Le helper résout le layout des champs (`parameterIsStruct: true`, `parameterStructSize`, `parameterStructFields` : nom/elementType/offset/size) et le natif compose l'immediate RDX depuis un texte `"Champ1=Valeur1,Champ2=Valeur2"` (`encodeStructParameterImmediate`, `clrElementTypeNameToKillcoreToken` dans `ApplicationController::callClrInstanceMethod`). Hors scope documenté : struct de 9-16 octets (paire de registres RDX+R8), plus de 8 octets (pointeur caché vers une copie), HFA — les variantes restantes de la convention d'appel x64 ne sont pas couvertes. **Vérifié bout en bout le 25/08/2026 via l'appli réelle** (PHASE 95) : `KillEngine.exe` piloté par le pipe d'automation, appel réel de `set_Waypoint(Coordinates{X,Y})` sur `KillEngineClrTestTarget`, oracle indépendant `getStatus` confirmant `waypointX=55/waypointY=77` et l'incrémentation du compteur de changements, cible vivante — pas seulement via `NativeSetterInvoker.cs` côté tests .NET. Correctif associé : l'injection utilise désormais un handle dédié `AllAccess` (l'ancien `m_handle` ReadOnly faisait échouer `VirtualAllocEx` en error=5, invisible des tests .NET qui ouvrent leur propre handle).
- Si `NativeCode` indique que la méthode n'a jamais été JITtée par le runtime cible, erreur claire ("le setter n'a jamais été appelé par le jeu — impossible de résoudre son adresse native, déclenche-le au moins une fois en jeu avant de réessayer") plutôt qu'une tentative de forcer la compilation JIT (impossible sans ICorDebug, hors scope total). **Détail vérifié par attache ClrMD réelle avant d'écrire le code** (pas deviné) : ClrMD 4.0.732401 rapporte `ulong.MaxValue` pour une méthode jamais JITtée, pas `0` — le code tolère les deux valeurs.
- Sécurité GC : l'adresse de l'objet et l'adresse native du setter sont résolues juste avant de construire/injecter le shellcode (fenêtre la plus courte possible), best-effort comme le reste du module pour les locators, pas une garantie.
- Si le setter lève une exception managée côté cible, aucune remontée propre n'est possible (pas de marshaling d'exception depuis un thread injecté) — risque documenté tel quel, pas géré.
- `verified` dans la réponse de `callClrInstanceMethod` ne signifie PAS "la valeur écrite correspond exactement" (contrairement à `writePrimitiveField`/`writePrimitivePath` qui connaissent le champ ciblé) : cette méthode générique ignore quel champ backing le setter modifie réellement. `verified=true` signifie "le thread distant a terminé dans le délai imparti (3000 ms) ET l'objet reste lisible via ClrMD ensuite" — preuve que l'appel n'a pas fait planter/corrompre la cible, pas une comparaison de valeur.

**Côté helper .NET** (`ClrSession.cs`, `MethodDispatcher.cs`) : voir `resolveInstanceMethodAddress` dans le tableau plus haut.

**Côté natif** (`apps/desktop/application_controller.cpp/.h`) : `Q_INVOKABLE QVariantMap ApplicationController::callClrInstanceMethod(objectAddressHex, methodName, valueText, valueType)`. Appelle `resolveInstanceMethodAddress` par RPC, parse `valueText` selon le type réel résolu (réutilise `killcore::parseValueType`/`killcore::parseScanValue`/`killcore::scanValueToBytes`, la même primitive que `writeMemoryValueConfirmed` — pas de parseur numérique réimplémenté ; `bool` est mappé sur `uint8` avec normalisation texte `true`/`false` → `1`/`0` avant délégation), construit l'immédiat 64 bits zero/sign-étendu selon la signedness du type, construit le shellcode (`buildCallInstanceMethodShellcode`) et l'injecte via `killcore::injectShellcode(m_handle, shellcode)`. Attend la fin du thread distant (`WaitForSingleObject`, timeout 3000 ms, même patron que `injectDll` dans `core/inject/dll_injector.cpp`), puis relit l'objet pour construire `verified`. Gardé par `confirmRiskAction('injection', ...)` côté frontend (`ui/src/stores/app.ts`), exactement comme `injectDllIntoProcess`/`installFunctionHook`/le speedhack — categoriquement différent d'une écriture ClrMD passive puisqu'il injecte et exécute du code dans le process cible.

**Côté frontend** : `ui/src/services/backend.ts` (`callClrInstanceMethod`), `ui/src/stores/app.ts` (action `callClrInstanceMethod`, ref `clrCallMethodResult`), `ui/src/views/ClrInspectorView.vue` (panneau "Appeler un setter (action avancée — injecte du code)", visuellement signalé avec le même langage `warning-band` ambre que le speedhack/l'injection DLL, bouton `btn-danger`).

**Preuve bout-en-bout réelle** : `Player.Vitality` (`tests/clr_targets/KillEngineClrTestTarget/ObjectGraph.cs`) a un vrai setter avec logique métier (clamp `[0, VitalityMax=999]`, compteur `_vitalityChangeCount` séparé du champ backing, synchronisation `IsAlive = false` quand la valeur atteint 0), avec un warmup unique dans `TestRoot.BuildGraph()` pour garantir qu'il est déjà JITté à l'attache. Voir la suite "appel de setter réel" plus haut pour le détail des tests xUnit dédiés (dont le test `double`/XMM1 ajouté en PHASE 59).

## PHASE 59 : écriture indexée de tableaux primitifs, locator auto-relocalisé, transaction atomique

Trois extensions livrées le même jour, indépendantes les unes des autres :

**Écriture directe par index dans un tableau/`List<T>` de primitifs** (`writePrimitivePath`, `ClrSession.cs`) : jusqu'ici, un chemin indexé (`Champ[i]`) ne savait écrire que des références d'objet (ex: `Inventory.Items[0]`). `IsIndexedFieldPrimitiveArray` inspecte désormais le type d'élément réel du champ collection ciblé et dispatche vers `WriteIndexedPrimitiveValue`/`ReadIndexedPrimitiveValue` quand l'élément est un primitif (`bool`/`int8..64`/`uint8..64`/`float`/`double`) — l'adresse de l'élément est résolue via `ClrType.GetArrayElementAddress` (la même primitive déjà utilisée côté lecture, `DescribeArray`/`ReadArrayElement`), écrite via `WriteProcessMemory` comme le reste du module, puis relue pour vérifier. **Hors scope explicite** : tableaux de STRUCTS imbriquées (élément value-type non primitif) — layouts internes trop complexes pour ce lot. Cas de test : `Player.Scores` (`int[]`, `ObjectGraph.cs`).

**Mutation par chemin symbolique auto-relocalisée après GC** (`ApplicationController::writeClrPrimitivePathByLocator`/`writeClrPrimitivePathBatchByLocator`, `apps/desktop/application_controller.cpp/.h`) : jusqu'ici, `writeClrPrimitivePath`/`Batch` exigeaient une adresse d'objet brute — l'appelant devait relocaliser manuellement via `findClrObjectsByFieldValue` en cas de GC compactant entre-temps. Ces deux nouvelles méthodes reprennent exactement le patron déjà utilisé par `resolveProfileTarget`/`activateProfileTarget` pour `LocatorKind::ClrField` : résolvent l'objet root via `findClrObjectsByFieldValue(typeSubstring, identityField, identityValue, 2)` (1 seul résultat attendu — erreur claire si 0 ou si le locator est ambigu, ≥2 résultats), PUIS délèguent aux méthodes d'écriture existantes (aucune logique d'écriture dupliquée). Aucune nouvelle méthode RPC côté helper .NET — composition purement native. UI : case à cocher "Utiliser un locator au lieu d'une adresse" dans le panneau `Écrire chemin`/`Transaction` existant (`ClrInspectorView.vue`), qui réutilise les champs type/champ identité/valeur du panneau locator déjà présent.

**Transaction multi-champs sous suspension coordonnée du runtime** (`ApplicationController::writeClrPrimitivePathBatchAtomic`) : `writePrimitivePathBatch` reste "best-effort" côté helper .NET (rollback inverse en cas d'échec) mais rien n'empêchait un autre thread du process cible — y compris le GC/JIT du CLR lui-même — de s'exécuter en parallèle pendant la séquence d'écritures. Cette méthode reprend le patron déjà utilisé par `writeMemoryValuesAtomic` (`killcore::ProcessThreadsSuspendGuard`, RAII, exclusion du thread appelant pour éviter un auto-deadlock) mais l'applique autour de **tout l'appel RPC** vers le helper ClrMD, pas seulement un `WriteProcessMemory` isolé — le helper .NET n'a besoin de rien savoir de cette suspension. **Risque documenté honnêtement, pas une atomicité parfaite** : suspendre toutes les threads du process cible pendant une opération ClrMD peut interagir avec le GC/JIT si l'un de ces sous-systèmes attendait un signal d'une thread désormais suspendue — best-effort, comme le reste du module pour les fenêtres GC des locators. UI : case à cocher "Suspendre le process pendant la transaction (plus sûr, plus risqué)" dans le panneau `Transaction` (masquée en mode locator, non combinée dans ce lot).

**Limite de preuve honnête pour ces trois extensions** : `ApplicationController` est un objet Qt/C++ hébergé par `KillEngine.exe`, sans harness d'automation Qt dans ce dépôt pour le piloter depuis xUnit (même limite déjà documentée pour le mécanisme shellcode ci-dessus). Les tests xUnit associés (`EndToEndTests.cs`) reproduisent donc le MÉCANISME sous-jacent directement via le pipe du helper ClrMD (locator + écriture, GC compactant réel, relecture) plutôt que d'appeler `ApplicationController` — la composition native elle-même (relocaliser-puis-déléguer, suspendre-puis-déléguer) n'est validée que par revue de code et build, pas par un test automatisé de bout en bout côté C++. Pour la transaction atomique en particulier : le test associé vérifie uniquement le résultat FONCTIONNEL (toutes les valeurs écrites et vérifiées) sous pression mémoire concurrente réelle (`GcChurnWorker` à taux élevé) — la garantie de suspension elle-même (« aucune autre thread n'a tourné pendant la fenêtre ») n'est pas prouvée par un test automatisé, ce serait de toute façon peu fiable à observer depuis l'extérieur.

## PHASE 65 : setters à paramètre objet/string, livré le 23/08/2026

Dernier volet non couvert de l'appel de setter réel (`resolveInstanceMethodAddress`/`callClrInstanceMethod`) : un paramètre non primitif. Décision arbitrée avec le propriétaire avant implémentation : possible **seulement** en pointant vers un objet/string **déjà existant** sur le tas managé (même convention que `writePrimitivePath` pour un changement de référence) — pas d'allocation d'un nouvel objet/string (demanderait d'appeler les helpers internes du CLR `JIT_NewObj`/`FastAllocateString` ou équivalents, hors de portée). Un paramètre `struct` reste non couvert à ce jour (voir "Scope — limites" plus haut).

**Détection type-valeur vs type-référence, vérifiée par attache ClrMD réelle avant d'écrire le code** (script jetable dans le scratchpad de session, attache sur `KillEngineClrTestTarget` réellement lancé) : `ClrMethod` (réflexion sur l'assembly ClrMD 4.0.732401 réellement restaurée, `typeof(ClrMethod).GetMembers()`) n'expose **aucune** API de résolution de type de paramètre — seulement `Signature` (string) et `MetadataToken`. La signature parsée seule (`ParseInstanceMethodParameters`) ne suffit donc PAS à distinguer un struct d'un type référence : les deux apparaissent identiquement comme un nom pleinement qualifié (`"KillEngine.ClrTestTarget.Item"` pour la classe `Item`, `"KillEngine.ClrTestTarget.Coordinates"` pour le struct `Coordinates`) — aucune information de forme dans le texte lui-même. Il faut donc résoudre le `ClrType` réel. `ClrModule` n'expose pas non plus de lecteur de métadonnées public (`MetadataAddress`/`MetadataLength` bruts existent, mais aucun parseur public exposé — l'`IAbstractMetadataReader` correspondant est interne). La résolution retenue, confirmée fonctionnelle par l'attache réelle : **`ClrHeap.GetTypeByName(string name)`** — appelée avec le nom pleinement qualifié extrait de la signature, elle résout un `ClrType` réel (recherche across tous les modules chargés, pas seulement le module déclarant, confirmé en résolvant `"System.String"` alors que `Player` est défini dans un module applicatif distinct de `System.Private.CoreLib`), avec `IsValueType` fiable dans les deux cas : `False`/`IsObjectReference=True` pour `KillEngine.ClrTestTarget.Item` (classe) et `System.String`, `True` pour `KillEngine.ClrTestTarget.Coordinates` (struct, testé même si aucun setter réel n'en prend un en paramètre — preuve que le garde-fou fonctionnerait si le cas se présentait). Détail supplémentaire confirmé par la même attache : `GetTypeByName` sur un nom primitif court (`"Int32"`, `"Double"`) renvoie `null` — cohérent avec le commentaire déjà présent dans le code sur `SupportedInstanceMethodParameterTypes` (les primitifs sont toujours rapportés en nom court, jamais en collision avec un nom pleinement qualifié), donc cette résolution n'est tentée QUE pour un paramètre déjà exclu de la liste des primitifs courts.

**Côté helper .NET** (`ClrSession.ResolveInstanceMethodAddress`) : si le paramètre n'est pas dans `SupportedInstanceMethodParameterTypes`, résout `runtime.Heap.GetTypeByName(parameterType)`. Type non résolu (générique, non chargé) → erreur claire, rejeté. `IsValueType == true` → erreur claire explicite (struct, hors scope permanent). Sinon → accepté, `parameterIsReferenceType: true` ajouté au résultat (`{success, objectAddress, typeName, methodName, nativeCodeAddress, parameterType, parameterIsReferenceType, isStatic}`) pour que le natif sache comment encoder l'argument.

**Côté natif** (`ApplicationController::callClrInstanceMethod`) : quand `parameterIsReferenceType` est vrai, `valueText` est interprété comme une adresse hex (`0x...`) d'un objet déjà existant — ou `"null"`/`"0"` pour effacer la référence (même convention que `ClrSession.ParseReferenceValue`, déjà utilisée par `writePrimitivePath`). Pour une adresse non nulle, l'adresse est validée via un appel `readObject` (helper ClrMD) **avant** de construire/injecter le shellcode — ne fait pas confiance à une adresse arbitraire fournie par l'appelant. `paramImmediate` reçoit directement cette adresse (RDX), sans conversion IEEE754/entière comme pour les primitifs — plus simple à encoder que le cas `float`/`double`. Le shellcode reste inchangé (`buildCallInstanceMethodShellcode` avec `paramIsFloat: false`) : `mov rcx, <this>; mov rdx, <adresseObjetParam>; mov rax, <nativeCodeAddress>; call rax`.

**Côté UI** (`ClrInspectorView.vue`) : le champ valeur existant du panneau "Appeler un setter" n'a pas été refondu — placeholder mis à jour ("Valeur, ou 0x... pour un paramètre objet/string existant") et `InfoDot` étendu pour documenter le nouveau cas. Le résultat affiche `parameterIsReferenceType` quand pertinent.

**Preuve bout-en-bout réelle** : `Player.EquippedItem` (`tests/clr_targets/KillEngineClrTestTarget/ObjectGraph.cs`) a un vrai setter à paramètre `Item` (référence) avec logique métier au-delà d'un simple stockage du champ backing — assigne `_equippedItem` ET synchronise `IsArmed` (`true`/`false` selon que la référence est non nulle), avec `EquipChangeCount` incrémenté séparément (même discipline de preuve que `Vitality`/`Vigor` : un raccourci d'écriture mémoire brute du champ backing ne produirait jamais ces effets de bord). ## PHASE 66 : écriture indexée d'un champ primitif dans un élément STRUCT de tableau, livré le 23/08/2026

`writePrimitivePath` savait déjà écrire un champ primitif à l'intérieur d'un struct DÉJÀ localisé (`field.GetAddress(structAddress, interior: true)`, ex: `Stats.Rank`) et résoudre l'adresse d'un ÉLÉMENT de tableau, struct ou non (`ClrType.GetArrayElementAddress`, déjà utilisée par `WriteIndexedPrimitiveValue`/lecture) — mais pas leur COMPOSITION : un chemin `Champ[i].SousChamp` où `Champ` est un tableau/`List<T>` de STRUCTS était rejeté dès la résolution de l'élément (`ResolveArrayReferenceElement` rejetait tout `componentType.IsValueType`), avant même d'atteindre la logique d'écriture de champ déjà capable de le gérer.

**Composition livrée** : `ResolveIndexedReference` (résolution d'un segment de chemin `Champ[i]` qui n'est PAS le dernier segment) retourne désormais un `PathNode` générique — référence d'objet (comportement historique) OU **struct** (nouveau) — au lieu d'un `ClrObject` fixe qui excluait par construction le cas struct. La fonction renommée `ResolveArrayElementNode` (ex-`ResolveArrayReferenceElement`) route vers `ClrArray.GetStructValue(index)` + `PathNode.FromValueType(...)` quand `componentType.IsValueType` est vrai, au lieu de rejeter. Une fois ce nœud struct retourné, le reste du pipeline (`ResolvePathSegment`/`WriteFieldOnPathNode`/`WriteFieldOnValueType`) le traite comme n'importe quel autre nœud struct déjà supporté — **aucune nouvelle primitive bas niveau écrite**, uniquement l'enchaînement des deux qui existaient déjà séparément.

**Limite d'origine, depuis partiellement levée** : au moment de ce chantier, le champ feuille devait être primitif — écrire l'élément struct ENTIER par index (`Champ[i]` en fin de chemin, pas suivi d'un champ) était explicitement hors scope. **PHASE 81 (24/08/2026) a levé cette limite pour le cas où TOUS les champs du struct sont primitifs** (`WriteIndexedStructValue`, format `"Champ1=Valeur1,Champ2=Valeur2"`, voir `WritePrimitivePath_UpdatesWholeStructArrayElementByIndex`) — écrire un élément struct ENTIER dont un champ est lui-même non primitif reste hors scope. ## Limitation connue, investiguée le 22/08/2026 (chantier "approfondissement CLR")

**Le root `StaticVar` (`TestRoot.RootPlayer`, champ static) n'apparaît toujours pas dans `heap.EnumerateRoots()`**, quelle que soit l'attache. Investigation menée réellement (script jetable dans le scratchpad de session, attache ClrMD réelle sur `KillEngineClrTestTarget`, pas de supposition) :

- **Piste 1 testée : `DataTarget.AttachToProcess(pid, suspend: true)`** (attache invasive) — **ne change rien** : `heap.EnumerateRoots()` rapporte toujours exactement les mêmes 37 roots (23 `StrongHandle`, 1 `PinnedHandle`, 13 `Stack`), aucun `StaticVar`, avec ou sans suspension du process cible.
- **Piste 2 testée : `DataTargetOptions.ForceCompleteRuntimeEnumeration = true`** (l'option existe bien dans ClrMD 4.0.732401, confirmé par réflexion avant de l'utiliser) — **ne change rien non plus**, seul ou combiné avec `suspend:true`.
- **Conclusion honnête** : sur ce runtime (.NET 8 CoreCLR) et cette version de ClrMD, `heap.EnumerateRoots()` ne semble simplement pas énumérer les racines statiques de type module/classe, indépendamment du mode d'attache — probablement une limitation du DAC lui-même sur CoreCLR plutôt qu'un problème de mode d'attache. **Ne pas re-tenter `suspend:true` en pensant que ça réglera ce point précis** : c'est vérifié négatif, documenté ici pour ne pas refaire l'investigation.
- **Résolution trouvée par un chemin différent** : ClrMD expose une API **complètement distincte** de l'énumération de roots pour lire un champ static directement — `ClrType.StaticFields` (`ImmutableArray<ClrStaticField>`) + `ClrStaticField.ReadObject(ClrAppDomain)` / `Read<T>(domain)` / `ReadString(domain)` / `IsInitialized(domain)` — et **cette API fonctionne parfaitement en attache PASSIVE** (`suspend:false`), sans invasivité. Les types sont retrouvés en parcourant `ClrModule.EnumerateTypeDefToMethodTableMap()` de chaque module chargé (`runtime.EnumerateModules()`) + `runtime.GetTypeByMethodTable(mt)` — nécessaire car un type purement static comme `TestRoot`, jamais instancié, n'apparaît pas dans `heap.EnumerateObjects()`. Nouvelle méthode `findStaticFields(typeSubstring, fieldNameSubstring?)` (`ClrSession.FindStaticFields`), vérifiée en conditions réelles : `TestRoot.RootPlayer` résolu à l'adresse exacte du `Player` vivant, `TestRoot.DisposableSlot` correctement rapporté `null` après un `dropDisposable`, `TestRoot.s_nextDisposableId` lu comme entier primitif — le tout **sans attache invasive**.
- **Décision délibérée** : puisque la résolution trouvée fonctionne déjà en mode passif, **aucun nouveau mode d'attache `suspended` n'a été introduit** — le principe fondateur du module (attache passive par défaut, capacité à relire un état post-GC sans réattacher) reste intact et non compromis. `findStaticFields` est une méthode additionnelle, pas un changement de comportement de `attach()`.
- **Reste non résolu** : `heap.EnumerateRoots()` lui-même ne rapportera jamais de root `StaticVar` sur cette configuration — si un futur besoin exige spécifiquement d'itérer *tous* les roots statiques de *tous* les types chargés (pas un type connu à l'avance), `findStaticFields` avec un filtre de type large peut approcher ce besoin mais reste une méthode différente d'un vrai remplacement de `EnumerateRoots`.

### 1. Vrai plus-court-chemin GCRoot (BFS multi-source)

`ClrSession.FindGcRootPath` (voir section "GCRoot chain complet" plus haut pour le mécanisme d'origine et ses limites, dont celle-ci fait partie) remplace la boucle "un BFS indépendant par root, avec son propre `HashSet<ulong> visited` local" par un **unique BFS multi-source** :

- Tous les objets de `heap.EnumerateRoots()` (bornés à `maxRootsScanned`) sont enfilés ENSEMBLE à la profondeur 0 dans une seule queue et un seul ensemble `visited` partagés. Dédoublonnage : si plusieurs roots pointent vers le même objet, il n'est enfilé qu'une seule fois — le premier root rencontré dans l'ordre d'énumération est celui rapporté comme origine si cet objet fait partie du chemin final retenu (choix déterministe, sans conséquence puisque toutes les sources de départ sont à égale profondeur 0).
- Un BFS explorant par profondeur croissante uniforme garantit que le PREMIER moment où l'objet cible est atteint correspond au plus court chemin en nombre de sauts parmi TOUTES les sources combinées — propriété standard d'un BFS multi-source, implémentée directement plutôt que re-démontrée.
- Chaque nœud visité porte un lien vers son parent dans le BFS (adresse + nature de la référence qui y mène) plutôt qu'une copie complète du chemin parcouru jusqu'ici (contrairement à l'ancienne version, qui copiait la liste de chemin à chaque enqueue) — le chemin final est reconstruit par remontée une fois la cible trouvée, légèrement plus efficace en mémoire au passage.
- **Mêmes bornes/budgets qu'avant, appliqués à la nouvelle structure** : `maxDepth`/`MaxGcRootPathDepth`, `maxRootsScanned`/`MaxGcRootsScanned`, `MaxGcRootPathArrayElementsPerNode`, `MaxGcRootPathTotalNodesVisited` (déjà un compteur GLOBAL dans l'ancienne version, pas de changement de sémantique), `GcRootPathTimeBudget`. **Pas de régression de performance sur un gros tas — au contraire** : chaque objet du tas n'est désormais exploré qu'une seule fois AU TOTAL, alors que l'ancienne version pouvait ré-explorer le même sous-graphe une fois par root qui l'atteignait.
- `shortestPathGuaranteed` passe de `false` à `true` dans le résultat retourné par cette implémentation — champ honnête : il n'existe plus de chemin de repli utilisant l'ancien algorithme dans ce lot, donc ce flag est toujours `true` quand `success:true`.
- **Format de retour inchangé** (`path`, `rootKind`, `rootAddress`, `rootObjectAddress`, `rootObjectTypeName`, `depth`, `rootsScanned`, `nodesVisited`, `elapsedMs`, `shortestPathGuaranteed`, `note`) — aucune modification requise côté `ApplicationController::findClrGcRootPath`/`backend.ts`/`app.ts`/`ClrInspectorView.vue`, qui consomment déjà cette méthode sans changement.

**Validé en conditions réelles** : le test déjà existant `FindGcRootPath_FindsPlausibleVerifiableChainFromRootToNestedItem` passe toujours tel quel dans son mécanisme de vérification saut par saut (seule son assertion sur `shortestPathGuaranteed` a été mise à jour de `False` à `True`, puisque c'est exactement le comportement que ce chantier change). Nouveau test dédié `FindGcRootPath_ReturnsTheShorterOfTwoDistinctPaths` : le graphe de test (`tests/clr_targets/KillEngineClrTestTarget/ObjectGraph.cs`) expose désormais deux chemins de longueurs différentes vers le même objet cible (`ShortestPathProbe`) — un chemin COURT (1 saut) via un second root `StrongHandle` dédié (`TestRoot.ShortestPathShortcutHandle` → `ShortestPathShortcut.Target` → `Probe`), et un chemin LONG (4 sauts) via le root existant `TestRoot.RootHandle` (`Inventory` → `LongChainStart` → `Next` → `Next` → `Leaf` → le MÊME `Probe`). Le test vérifie que `findGcRootPath` retourne bien le chemin à 1 saut (`depth == 1`, `rootObjectTypeName` contient `ShortestPathShortcut`), puis vérifie indépendamment (par lecture directe via `readObject`, sans passer par `findGcRootPath`) que le chemin à 4 sauts existe bel et bien aussi dans le graphe réel — la preuve porte donc sur un choix RÉEL entre deux chemins effectivement présents, pas un cas fabriqué à sens unique.

**Solidité : mécanique et solide** — le changement d'algorithme est une réécriture localisée et bien circonscrite (un seul point d'entrée, format de sortie inchangé), couverte par un test qui prouve concrètement la propriété centrale du chantier (le plus court des deux gagne) plutôt que de se contenter de revalider le mécanisme déjà couvert par le test existant.

### 2. `LinkedList<T>` et `SortedDictionary<K,V>`/`SortedSet<T>` dans le déballage (`readObject`)

Layouts internes vérifiés par attache ClrMD réelle sur `KillEngineClrTestTarget` (script jetable dans le scratchpad de session, pas deviné), même méthodologie que le chantier `HashSet<T>`/`Queue<T>`/`Stack<T>` du 22/08/2026 :

- **`LinkedList<T>`** : PAS de buffer tableau — chaîne de nœuds `LinkedListNode<T>` (une CLASSE, pas une struct) reliés par les champs d'instance `next`/`prev` (minuscule), chaque nœud portant sa valeur dans le champ `item` (minuscule). La liste elle-même expose `head` (le premier nœud logique, `null` si vide) et `count`. **Confirmé CIRCULAIRE en interne** par attache réelle (vérifié concrètement avec une séquence `AddFirst`/`AddLast`/`Remove` qui produit 3 nœuds vivants) : en partant de `head` et en suivant `next`, le dernier nœud logique a bien `next` qui pointe DE NOUVEAU vers `head`, jamais vers `null` — la sortie de boucle se fait donc par comptage (`count` nœuds parcourus) et/ou détection du retour à l'adresse de `head`, jamais en attendant un `next` null qui n'arrive pas.
- **`SortedDictionary<K,V>`/`SortedSet<T>`** : implémentés via un arbre rouge-noir interne, **partagé par les deux types** — vérifié par attache réelle : `SortedDictionary<K,V>` délègue à un champ privé `_set` de type `TreeSet<KeyValuePair<K,V>>`, qui expose `count` et `root` ; `SortedSet<T>` expose `root`/`count` directement sur lui-même. Les deux s'appuient sur la MÊME classe de nœud générique `SortedSet<T>+Node`, dont les propriétés auto-implémentées produisent des champs backing `<Left>k__BackingField`/`<Right>k__BackingField`/`<Item>k__BackingField`/`<Color>k__BackingField` (`Color`, l'équilibrage rouge-noir, n'est pas lu — non nécessaire pour restituer le contenu). Un parcours EN ORDRE (in-order : gauche, nœud, droite) d'un arbre binaire de recherche produit naturellement les éléments TRIÉS sans réimplémenter de logique de comparaison — implémenté de façon ITÉRATIVE (pile explicite, pas de récursion), borné par le nombre d'éléments demandés (`MaxCollectionItems=32`) ET par une garde `MaxSortedTreeNodesVisited` contre une structure corrompue/dégénérescente (un arbre rouge-noir bien formé garantit une hauteur O(log n), donc cette seconde borne ne devrait jamais être le facteur limitant en usage normal — elle protège un scénario anormal, pas un cas légitime).
- **Piège réel rencontré pendant la vérification, documenté dans le code** (`ClrSession.ReadFieldValue`) : pour un champ dont le type déclaré est un PARAMÈTRE GÉNÉRIQUE `T` instancié en référence (ex. `LinkedListNode<string>.item`), ClrMD rapporte `field.ElementType == Class` (partage de code générique canonique côté CLR pour les types référence), **PAS** `ElementType.String`, même quand le type réel résolu de l'instance (`field.Type.Name`) est bel et bien `"System.String"`. Le check `ElementType.String` en tête de `ReadFieldValue` (qui suffit pour un champ `string` DIRECT non générique, ex. `Player.Name`) ne suffisait donc pas pour ce cas précis — sans correctif, un `LinkedList<string>` aurait affiché ses éléments comme des références objet génériques (`{address, typeName}`) plutôt que le texte réel. Corrigé en ajoutant le même garde-fou déjà en place pour les champs struct dans `ReadValueTypeFieldValue` (`refObj.Type?.IsString == true` → `refObj.AsString(...)`) au chemin des champs objet directs — correctif général qui bénéficie à tout futur champ générique-référence rencontré ailleurs dans le module, pas seulement à `LinkedList<T>`.
- Bornes identiques au reste du module (32 éléments max par collection, cohérent avec `MaxCollectionItems` existant).
- **`ConcurrentDictionary<K,V>` couverte depuis PHASE 80 (24/08/2026)** — `DescribeConcurrentDictionary` (`ClrSession.cs`), layout `_tables._buckets`/`_countPerLock` vérifié par attache ClrMD réelle. **`ConcurrentStack<T>` couverte depuis PHASE 202 (29/08/2026)** — `DescribeConcurrentStack` suit `_head` puis `_next` et restitue les valeurs en ordre LIFO.
- **`ConcurrentQueue<T>` couverte depuis PHASE 222 (30/08/2026)** — `DescribeConcurrentQueue` (`ClrSession.cs`). C'est bien la structure "segmentée" explicitement laissée ouverte par PHASE 202 (voir commentaire du test `ReadObject_UnpacksConcurrentStackInLifoOrder`, "chantier plus risqué des structures segmentées/work-stealing") — layout vérifié en deux temps : (1) reflection sur le runtime .NET local (script jetable), PUIS (2) validation empirique de l'algorithme candidat contre `ConcurrentQueue<T>.ToArray()` sur 8 scénarios (vide, séquentiel, dequeue partiel, multi-segment, wrap-around post-dequeue+reenqueue, drain complet + refill, frontière de segment traversée par un dequeue partiel) avant d'écrire une seule ligne de `ClrSession.cs` — même discipline "vérifié, pas deviné" que le reste du module, appliquée ici à un algorithme plutôt qu'à un layout de champs. Structure interne : `_head`/`_tail` (classe `ConcurrentQueueSegment<T>`, chaînée via `_nextSegment`, jamais circulaire), chaque segment portant un buffer `_slots` (`Slot[]`, struct `Item`+`SequenceNumber` — PAS un tableau de `T` brut, c'est l'algorithme MPMC borné de Vyukov) et `_slotsMask` (capacité - 1, toujours une puissance de 2). `_headAndTail` (struct `PaddedHeadAndTail`, champs `Head`/`Tail` en `int`) donne une plage de POSITIONS LOGIQUES (pas des index de tableau) ; pour une position `pos` dans `[Head, Tail)`, l'index physique est `pos & _slotsMask`, et le slot n'est réellement peuplé que si `slot.SequenceNumber == pos + 1` (un slot jamais écrit porte son propre index, jamais `index + 1` — c'est ce qui distingue "jamais écrit" de "écrit puis potentiellement déjà consommé"). Ignorer cet invariant aurait produit des items périmés ou pas encore publiés. Test dédié `ReadObject_UnpacksConcurrentQueueAcrossSegmentBoundaryInFifoOrder` (`EndToEndTests.cs`) : le graphe de test (`Inventory.ConcurrentEvents`, `ObjectGraph.cs`) enqueue 40 éléments (capacité initiale de segment = 32, donc un deuxième segment est forcé) puis en dequeue 35 — exerce délibérément la traversée de frontière de segment plutôt que le seul cas à un segment.
- **`ConcurrentBag<T>` couverte depuis PHASE 225 (30/08/2026)** — `DescribeConcurrentBag` (`ClrSession.cs`). Structure work-stealing à affinité de thread, layout vérifié en deux temps comme `ConcurrentQueue<T>` avant elle : (1) reflection sur le runtime .NET local (script jetable), PUIS (2) validation empirique de l'algorithme candidat contre `ConcurrentBag<T>.ToArray()` sur 10 scénarios (vide, ajouts simples, churn local sans croissance, croissance au-delà de la capacité initiale, drain complet + réajout, plusieurs threads = plusieurs files distinctes, vol cross-thread après mort du thread propriétaire, vol ET croissance combinés, une file entièrement vidée à côté d'une autre vivante) avant d'écrire une seule ligne de `ClrSession.cs`. Structure interne : `_workStealingQueues` (classe imbriquée `WorkStealingQueue`, PAS une struct) est la TÊTE d'une liste chaînée via `_nextQueue` — une file par thread producteur, la plus récemment créée en tête. **Piège réel évité par la validation empirique plutôt que supposé** : chaque file porte un champ `_mask`, par analogie avec `ConcurrentQueueSegment<T>` on s'attendrait à un wraparound modulo — FAUX ici, confirmé concrètement : `_headIndex`/`_tailIndex` sont des indices PLATS dans `_array`, et après une croissance de capacité l'ancien contenu est copié aux MÊMES indices dans le nouveau tableau plus grand (`_headIndex`/`_tailIndex` préservés tels quels, jamais réinitialisés) — `_mask` sert uniquement à l'arithmétique de doublement de capacité, pas à l'adressage circulaire. `_headIndex` n'avance QUE par un vol (`TryTake` depuis un AUTRE thread, retire par le DÉBUT, FIFO) ; `_tailIndex` avance/recule par les Add/Take LOCAUX du thread propriétaire (à la FIN, LIFO) — le contenu valide d'une file est donc l'intervalle `[_headIndex, _tailIndex)`, énuméré en ORDRE INVERSE pour matcher `ToArray()`. Une file entièrement vidée (`_headIndex == _tailIndex`) reste dans la liste chaînée sans contribuer d'élément, et le thread propriétaire peut être mort sans que la file disparaisse ni que sa lecture change. Test dédié `ReadObject_UnpacksConcurrentBagAfterCrossThreadStealFromDeadOwner` (`EndToEndTests.cs`) : le graphe de test (`Inventory.ConcurrentTraces`, `ObjectGraph.cs`) fait ajouter 6 éléments par un thread qui meurt ensuite, puis le thread principal vole 2 éléments — exerce délibérément `_headIndex > 0` sur une file dont le propriétaire n'existe plus.

Nouvelles méthodes `DescribeLinkedList`/`DescribeSortedDictionary`/`DescribeSortedSet` (`ClrSession.cs`), câblées dans le dispatch existant de `DescribeCollection`. Graphe de test étendu (`Inventory.LinkedTags`/`SortedCurrencies`/`SortedScores`, `ObjectGraph.cs`), peuplé dans un ORDRE D'ALLOCATION délibérément différent de l'ordre logique attendu (`AddLast`/`AddFirst`/`Remove` pour la liste chaînée ; insertions désordonnées pour les deux collections triées) pour prouver que `readObject` restitue bien l'ordre LOGIQUE et pas l'ordre d'allocation mémoire.

**Validé en conditions réelles** : test dédié `ReadObject_UnpacksLinkedListSortedDictionaryAndSortedSetInLogicalOrder` — vérifie que `LinkedTags` restitue `["first", "second", "third"]` (ordre chaîné logique après le `Remove`, pas l'ordre d'allocation), que `SortedCurrencies` restitue les entrées triées par clé (`copper`, `gold`, `silver`, insérées dans le désordre `silver`/`copper`/`gold`), et que `SortedScores` restitue les valeurs triées (`7, 15, 42, 99`, insérées dans le désordre `42, 7, 99, 15`).
